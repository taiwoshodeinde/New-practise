This PRD turns *Gmail Setup Guide for FinMail Agent* (October 24, 2026) into a product surface. The guide is the source of truth for sequence, scope order, environment variable names, and failure modes. Where the guide is a 15-part document for a terminal, this PRD specifies the screen that replaces it.

---

## 2. Executive Summary

### Problem Statement

The mailbox owner who wants FinMail to read financial email must complete a Google Cloud project, a consent screen, a test user, a Desktop OAuth client, a local token, and a connection test, in an order where one wrong click (`Web application` instead of `Desktop app`, a missing test user, send scope too early) blocks the agent with errors that look unrelated to the mistake.

### Solution

A **local setup console** served only on `127.0.0.1` walks that owner through one Google decision at a time, checks the artifact each step should produce, and refuses to unlock sending until read access is proven. Daily triage stays on the WhatsApp thread the agent already uses: digest, draft, and an explicit `send N` approval. Secrets (`credentials.json`, `token.json`) stay on the machine. The console never uploads them.

### Core Value Proposition

Connect your own Gmail to FinMail in one sitting, see proof that the right mailbox is connected, and keep sending switched off until you deliberately turn it on.

### Success Metrics

| KPI | Definition | MVP target |
|-----|------------|------------|
| Setup completion rate | Owners who reach “Connected as {address}” divided by owners who pass the prerequisites screen | 80% |
| Time to first proof | Median minutes from Welcome to a successful connection test | ≤ 25 minutes (guide budget is ~20) |
| Wrong-client-type rate | Setups that hit `redirect_uri_mismatch` because the OAuth client was not Desktop | < 5% |
| Premature send rate | Owners who enable `gmail.send` before a successful read test | 0% (gated in the UI) |
| Recovery without the guide | Share of Part 14 symptoms resolved from the Troubleshooting screen without opening the markdown guide | 90% of in-scope symptoms |

## 3. User Research & Personas

### 3a. Target Audience Overview

FinMail is a single-owner agent. It watches one Gmail mailbox for financial mail (invoices, receipts, statements), drafts replies, and sends only after the owner approves a specific draft. The owner is technical enough to run Python and use Google Cloud Console, and busy enough to abandon a 15-part guide when a step’s wording drifts from Google’s current console. There is no multi-tenant admin and no end-user who receives FinMail as a product. The only human in the interface is the mailbox owner. Google’s consent screen is a third-party surface we do not own; the console must prepare the owner for it instead of pretending it is ours.

Two account shapes matter, and they diverge at the consent screen:

- **Personal Gmail (`@gmail.com`)** — Google user type External, Publishing status Testing, the owner must be listed as a test user, and refresh tokens can expire after about 7 days until the app is published.
- **Google Workspace, same organization** — user type Internal. No test-user list and no 7-day testing expiry. Sending this owner down the External path creates work they do not need.

### 3b. User Personas

#### Persona 1 — Primary

| Field | Detail |
|-------|--------|
| **Name & Role** | Ade, 34, independent consultant and the only mailbox FinMail will read |
| **Goals** | Finish Gmail setup once, trust that FinMail sees invoice mail, and keep the agent from emailing anyone until a draft looks right |
| **Pain Points** | Google’s console renames menus; the “unverified app” warning feels like a virus alert; a 403 three steps later does not point back to the missed test user |
| **Tech Comfort** | Medium. Comfortable with a terminal command that is shown in full. Unwilling to debug OAuth from memory |
| **Usage Context** | One evening at a laptop, Gmail open in the same browser, about 20 minutes. Returns days later only when the token expires or a send is ready |
| **Key Needs** | One next action. Proof of the connected address. A kill switch that is visibly off |

#### Persona 2 — Primary variant

| Field | Detail |
|-------|--------|
| **Name & Role** | Ruth, 41, operations lead at a small Workspace company, connecting the finance inbox she administers |
| **Goals** | Use an Internal consent screen, avoid a public testing-mode app, and hand a locked-down `token.json` to the server that already runs the agent |
| **Pain Points** | Guides written for `@gmail.com` tell her to add test users and publish the app. Neither applies, and following them would be wrong |
| **Tech Comfort** | High. She will `chmod 600` a file if the screen says which file and why |
| **Usage Context** | Office laptop for the browser consent, then a copy to the server. She may not complete OAuth on the server because it has no display |
| **Key Needs** | An explicit Internal path. A server handoff checklist. File permission guidance next to the copy step |

#### Persona 3 — Returning owner

| Field | Detail |
|-------|--------|
| **Name & Role** | Ade, two weeks later, when the agent reports an invalid token |
| **Goals** | Re-authorize without recreating the Google Cloud project or loosening scopes |
| **Pain Points** | “Invalid grant” does not say whether to redo all 15 parts or only the browser approval |
| **Tech Comfort** | Medium, lower patience than on day one |
| **Usage Context** | Interrupted, often from a WhatsApp alert that the agent could not read mail. Wants the shortest repair |
| **Key Needs** | A symptom that maps to a single repair. Confirmation that `credentials.json` is still valid and only `token.json` must be replaced |

### 3c. Jobs-to-Be-Done

> When I have a new Gmail mailbox and a Python agent that cannot see it, I want a single next step that matches Google’s current console, so I can stop reconstructing the setup from a long document.

> When Google shows “This app isn’t verified,” I want to know that warning is expected for my own app and which control to press, so I can finish consent without granting a scope I did not intend.

> When read access works, I want sending to stay impossible until I add `gmail.send`, mint a new token, and pass a send-to-self test, so a draft cannot leave the mailbox early.

> When the agent is moved to a machine without a browser, I want to approve access on my laptop and carry only the token, so the server never has to open Google’s consent screen.

> When mail stops with `invalid_grant` or `access_denied`, I want the exact missed step named, so I repair that step instead of creating a second Google Cloud project.

## 4. Information Architecture

### Navigation model

**Desktop (1024px and up):** a persistent left rail. Setup is a one-time job with a long return tail (token health, send upgrade, server move). A rail keeps completed steps visible, which a wizard-only stack would hide. The rail is the orientation; the page has one primary action.

**Narrow viewports (under 1024px):** the rail collapses into a top progress control labeled “Step 4 of 8 · Test user.” Setup is specified for a laptop. The narrow layout exists so a step can be followed beside Google Cloud on a smaller window, not as a phone-first product. WhatsApp remains the phone surface.

There is no marketing site, no multi-user account switcher, and no hamburger full of future modules. Items the owner must not use yet are visible and disabled, with the reason on the item (progressive disclosure without hiding the safety model).

### Screen inventory and hierarchy

```
FinMail Agent
├── Local setup console (http://127.0.0.1 only)
│   ├── Welcome
│   ├── Prerequisites
│   ├── Connect Gmail
│   │   ├── 1. Create the Google Cloud project
│   │   ├── 2. Enable the Gmail API
│   │   ├── 3. Configure the consent screen
│   │   ├── 4. Add yourself as a test user
│   │   ├── 5. Add the read-only scope
│   │   ├── 6. Create the Desktop OAuth client
│   │   ├── 7. Authorize this mailbox
│   │   └── 8. Prove the connection
│   ├── Home / Connection
│   ├── Enable sending
│   ├── Move to server
│   ├── Troubleshooting
│   ├── Security checklist
│   └── Settings
│       ├── Paths and environment
│       ├── Dry run and kill switch
│       └── Revoke Google access
└── WhatsApp owner thread (channel we do not chrome; message patterns we do specify)
    ├── Connection and token alerts
    ├── Financial mail digest
    ├── Draft review
    └── Send confirmation
```

### Entry points

| Destination | How the owner arrives |
|-------------|------------------------|
| Welcome | First launch, when `token.json` is absent |
| Home / Connection | Any later launch once a token exists and the profile call succeeds |
| The incomplete wizard step | Later launch when a token is missing or the last completed step was recorded in local `agent_state.json` |
| Troubleshooting, opened on a symptom | A failed check in the wizard, a failed test on Home, or a WhatsApp alert the owner taps through to the console |
| Enable sending | Home, only after the read test has succeeded in this state file |
| Move to server | Home, secondary action, available after the read test |
| Settings | Rail item, always available after Welcome is dismissed |
| WhatsApp digest | The agent’s existing poll, after `fetch_emails` returns matches for the configured Gmail query |

## 5. User Flows

### Flow: First-run setup

```
Flow Name: First-run setup
Trigger: Owner starts the console and no token.json is present
Happy Path: Welcome → Prerequisites (all four pass) → Steps 1–6 → credentials.json detected → Step 7 browser consent → token.json saved → Step 8 shows address and message count → Home
Alternate Paths:
  - Owner chooses Workspace Internal at Step 3 → Step 4 is marked Not required and skipped → Step 5
  - Owner already has credentials.json in the project folder → Steps 1–6 show as “Confirm” with a pass chip if the file parses as a Desktop client → they can still open each step
Exit Points:
  - Close during Steps 1–6: resume on the first incomplete step; Google-side work already done is not repeated if the owner marks it done
  - Close during Step 7 after Allow but before the success callback: Step 7 offers “Check for token.json” before asking them to start consent again
```

### Flow: Connect and prove read access (core task)

```
Flow Name: Prove the mailbox connection
Trigger: Owner reaches Step 8, or presses Test connection on Home
Happy Path: Console calls the local test (profile + list 5 messages) → “Connected as ada@gmail.com” and “Messages found: N” → primary rail unlocks Home as the default
Alternate Paths:
  - API just enabled and Google returns 403 accessNotConfigured → inline error names Part 2, offers Wait and retry, does not send them back to Step 1
  - Token file exists but scopes do not include gmail.readonly → error names Step 5 and re-authorization, not a new project
Exit Points:
  - Owner leaves on a failing test: Home stays in “Not proven” and the next launch opens Step 8 with the last error preserved
```

### Flow: Google mailbox authorization

```
Flow Name: Authorize this mailbox
Trigger: Owner presses Open Google consent on Step 7
Happy Path: Local server starts on a free port → system browser opens Google account chooser → owner picks the test-user address → unverified-app interstitial → Advanced → Go to FinMail Agent → Allow “view your email messages and settings” → browser shows a one-line success → console detects token.json and advances
Alternate Paths:
  - Owner picks a different Google account than the test user → consent returns access_denied → Step 7 explains the address mismatch and links to Step 4, with the address they added shown if they typed it
  - Browser does not open (no display, or popup blocked) → Step 7 shows the localhost URL to copy and states that a server without a browser must use Move to server after a laptop authorization
Exit Points:
  - Owner closes the Google tab: Step 7 returns to its idle state, no token is written, no error banner implies failure of the whole setup
```

There is no FinMail username or password in v1. “Forgot password” does not exist. Recovery of access is re-authorization or revoke-and-authorize, specified in Troubleshooting and Settings.

### Flow: Something failed

```
Flow Name: Recover from a known Gmail setup error
Trigger: A check fails, or the owner opens Troubleshooting and picks a symptom
Happy Path: Symptom card → one likely cause in plain language → one primary repair that deep-links to the responsible step → owner re-runs only that check
Alternate Paths:
  - Symptom is “Google hasn’t verified this app” → the card says this is expected and shows the Advanced path; it is not treated as a defect
  - Symptom is not in the Part 14 list → card says the console does not recognize it, shows the raw Google message in a monospace block the owner can copy, and offers the security note that the message must not include file contents
Exit Points:
  - Owner retries the same check three times with the same error code: the card stops auto-retry and tells them to wait (API propagation) or to confirm the project name in the Google top bar
```

### Flow: Enable sending (after read access works)

```
Flow Name: Turn on approved sending
Trigger: Owner opens Enable sending from Home after a successful read test
Happy Path: Read the consequence panel → confirm Dry run is on → add gmail.send in Google Data Access → console accepts only after the owner checks “I saved the new scope” → delete old token and re-authorize → send-to-self test with To locked to the connected address → owner sees the message id → SEND_ENABLED stays off until they explicitly arm it
Alternate Paths:
  - Owner tries to open Enable sending before Step 8 passes → screen explains that sending stays locked and links to Step 8
  - Send-to-self returns 403 insufficient scopes → repair is “token was minted before the scope changed”; the screen deletes the instruction to reuse token.json and restarts re-authorization
Exit Points:
  - Owner completes the scope and the new token but skips send-to-self: Home shows Sending as “Scoped, not tested”; the WhatsApp send command stays refused
```

## 6. Screen-by-Screen Specifications

### Screen: Welcome

**Purpose**
Set the contract for the next 20 minutes: what will exist at the end, what FinMail will not do yet, and that this window talks only to the local machine.

**Layout Structure**

- Top bar: wordmark “FinMail,” no account menu.
- Primary zone, max width 640px, centered: outcome, time, and a single start button.
- Secondary zone under the button: three facts (local only, read-only first, one mailbox).
- No rail yet. The rail appears once the owner leaves Welcome, so the first screen is not a dashboard of locked items.

**UI Components**

| Component | Type | State(s) | Behavior |
|-----------|------|----------|----------|
| Outcome list | Static definition list | Default | Four rows matching the guide’s end state: Cloud project, `credentials.json`, `token.json`, a proven connection. Sending is listed as “later,” in `color-text-secondary` |
| Start setup | Primary button, LG, 48px height | Default, Hover, Focus | Navigates to Prerequisites. No loading state; nothing is called |
| Already connected | Ghost button | Default; Hidden if no `token.json` | If a token file is present, this is the primary button and Start becomes secondary. Routes to Home |
| Local-only note | Inline note | Default | “This page is served on your computer. FinMail does not receive your credentials file.” |

**User Actions**

- Start setup.
- Continue to Home when a token already exists.
- No skip of the outcome list.

**Interactions & Transitions**

- Navigation into Prerequisites is a 200ms cross-fade. The rail slides in from the left at the same time, 240ms `ease-out`.
- No illustration carousel and no autoplay.

**Data & Content**

- Presence of `token.json` at `GOOGLE_TOKEN_PATH` if set, otherwise `./token.json`. The console reads the filesystem through its local process. It displays the filename, never the file body.
- Copy is fixed. No remote CMS.

**Empty State**
Not a data screen. First launch is this screen’s normal state.

**Error State**
If the process cannot read its own working directory, replace the start button with: “FinMail cannot read this folder.” Show the absolute path and a Retry button. Do not offer a file upload on Welcome.

**Accessibility Notes**

- `h1`: “Connect Gmail to FinMail.”
- Start is the first tab stop after the skip-to-content link.
- The local-only note is text, not only a lock icon.

**UX Rationale**
The guide opens with an outcome table because owners need to know the job is finite. The screen keeps that table and removes every other decision (Hick’s Law). Hiding the rail until the second screen avoids a wall of disabled destinations on minute zero.

### Screen: Prerequisites

**Purpose**
Stop the owner before Google Cloud if the machine cannot finish the job. Four checks, each with a pass, a fail, and a repair.

**Layout Structure**

- Rail visible, Prerequisites marked current.
- Header: “Before you start.”
- Content: a vertical list of four check rows.
- Sticky footer action bar: Back (ghost) and Continue (primary), Continue disabled until all required checks pass.

**UI Components**

| Component | Type | State(s) | Behavior |
|-----------|------|----------|----------|
| Check row | List item with status icon | Checking, Pass, Fail | Icon plus text. Color is never the only signal: label reads Pass or Fail |
| Gmail account | Check | Pass when the owner types an address and confirms it is the mailbox to read; Fail when empty | Email input, not a live Google check. Helper: “Use the address you will add as a test user.” |
| Python 3.10+ | Check | Pass / Fail from `python3 --version` via the local process | Fail copy includes the version found, or “Python 3 was not found on PATH.” |
| Browser on this machine | Check | Pass if the platform reports a display and a browser; Fail on a headless host | Fail does not block a “I’ll authorize on a laptop” path: a secondary radio, “This machine has no browser,” switches the flow toward Move to server and disables Step 7’s auto-open |
| Time and project note | Static text | Default | “About 20 minutes. Use a new Google Cloud project named FinMail Agent.” |
| Continue | Primary button | Enabled, Disabled | Disabled until Gmail address and Python pass, and either Browser passes or the no-browser radio is selected |

**User Actions**

- Edit the mailbox address.
- Re-run checks.
- Choose the no-browser path.
- Continue.
- Back to Welcome.

**Interactions & Transitions**

- Checks run on entry. Each row resolves independently; do not block the list on the slowest check.
- A failing row expands its repair in place, 150ms. No modal.

**Data & Content**

- Mailbox address is stored in `agent_state.json` as `mailbox_address`. It is a hint for later mismatch errors, not proof of ownership.
- Python version string from the local interpreter.

**Empty State**
Rows start in Checking with a skeleton bar (8px height) in place of the detail line. If a check has not returned in 3 seconds, the detail line reads “Still checking…”

**Error State**
A check that throws shows Fail plus the one-line reason. The page does not become a full-screen error unless the state file cannot be written.

**Accessibility Notes**

- The list is a `ul`. Each status is text (“Pass”, “Fail”, “Checking”).
- Continue exposes `aria-disabled` and a live region: “Continue is unavailable until Python and the mailbox address pass.”

**UX Rationale**
The guide’s “Before you start” is four bullets that owners skip. Making Python and the browser into gates prevents the most expensive failure: finishing Google’s console on a machine that cannot open the consent browser. The address is collected now so Step 4 and the `access_denied` repair can show the same string back.

### Screen: Connect Gmail (shared wizard chrome)

**Purpose**
Hold the eight Google-side and local-side steps in one frame so each step page only has to specify its decision.

**Layout Structure**

- Left rail: Home (disabled until Step 8 passes), Connect Gmail expanded to show steps 1–8, Enable sending (disabled), Move to server (disabled), Troubleshooting, Security, Settings.
- Step header: “Step {n} of 8” as caption, step title as `h1`, one-sentence purpose.
- Main column, max 720px: instruction, the decision, then proof.
- Right side on desktop only, 280px: “You are in project FinMail Agent” reminder, plus the account type chosen at Step 3 once it is known. Hidden below 1024px; the reminder moves under the title.
- Footer: Back, and a primary button named for the step’s proof (“I created the project”, “Check again”, “Authorize”).

**UI Components**

| Component | Type | State(s) | Behavior |
|-----------|------|----------|----------|
| Step rail item | Navigation link | Upcoming, Current, Done, Skipped, Blocked | Done shows a check and remains openable. Skipped is used only for Step 4 on Internal. Blocked is not used inside 1–8; order is recommended, not a hard lock, except Step 8’s success gate for later sections |
| Open in Google | Secondary button | Default | Opens a named Google Console URL in a new tab. `rel` is irrelevant on a local app; the visible label includes the destination (“Open APIs & Services”) |
| Mark done | Primary button | Default, Disabled | Disabled until the step’s required confirmation checkbox is checked, where the step has one. Writes the step id and timestamp into `agent_state.json` |
| External link warning | Text under the Google button | Default | “Google’s labels move. If the page does not match, use Troubleshooting rather than a second project.” |

**User Actions**

- Move between steps from the rail, including backwards.
- Open the relevant Google screen.
- Mark the step done, or re-open a done step and clear it.

**Interactions & Transitions**

- Changing steps swaps the main column with a 150ms fade. The rail selection is instant.
- Progress is remembered if the process restarts.

**Data & Content**

- Step status from `agent_state.json` keys `steps.project`, `steps.api`, `steps.consent`, `steps.test_user`, `steps.readonly_scope`, `steps.client`, `steps.authorized`, `steps.proven`.
- Values are `pending`, `done`, `skipped`, or `failed` plus an optional `last_error` code.

**Empty State**
A step with no local artifact yet shows the instruction, not a zero-data illustration. The absence of `credentials.json` or `token.json` is the empty state and is described on Steps 6–8.

**Error State**
Wizard-level failures (state file unwritable, port 127.0.0.1 unavailable) use a banner at the top of the main column: what failed, the path or port, Retry. They do not clear completed steps.

**Accessibility Notes**

- Rail is a `nav` with `aria-current="step"` on the active step.
- “Step 4 of 8” is visible text, not only a progressbar. A progressbar may mirror it if it has `aria-valuenow`.
- Focus moves to the step `h1` on step change.

**UX Rationale**
Eight steps match the eight decisions in Parts 1–9 of the guide (folder, venv, and code drop-in stay off this rail; they are prerequisites or engineering work, not owner decisions). Showing status in the rail rewards progress and makes the Internal skip visible instead of silently renumbering.

### Screen: Step 1 — Create the Google Cloud project

**Purpose**
Get a new project named `FinMail Agent` selected in the console the owner will use for every later step.

**Layout Structure**
Shared wizard chrome. Main column is a numbered list of six instructions and a confirmation.

**UI Components**

| Component | Type | State(s) | Behavior |
|-----------|------|----------|----------|
| Open Google Cloud | Secondary button | Default | Opens `https://console.cloud.google.com` in a new tab |
| Instruction list | Ordered list | Default | 1. Sign in with the Google account for this project. 2. Accept terms if asked. 3. Project picker → New project. 4. Name exactly `FinMail Agent`. Leave Organization as default. 5. Create, then select that project. 6. Confirm the name in the top bar |
| Project name confirmation | Checkbox | Unchecked, Checked | Label: “The top bar shows FinMail Agent, and it is a new project.” Required before Mark done |
| Mark done | Primary button | Disabled until checked | Records `steps.project = done` |

**User Actions**

- Open Google Cloud.
- Confirm the project name.
- Mark done. Go back to Prerequisites.

**Interactions & Transitions**
Checking the box enables the primary button immediately (no animation beyond the button’s enabled color, 150ms).

**Data & Content**
No Google API call. The console cannot see the Cloud project. The confirmation is an attestation, and later errors that mention the wrong project point back here in their repair copy.

**Empty State**
The unchecked box is the empty state.

**Error State**
None local. If the owner later hits a 403, Troubleshooting tells them to re-check the top-bar project name rather than this screen showing a false error now.

**Accessibility Notes**
The checkbox label is the full sentence, not “Confirm.”

**UX Rationale**
A wrong or unselected project makes every later 403 look like an API bug. The screen makes the project name a typed constant (`FinMail Agent`) and the top-bar check an explicit act, which is the guide’s own “everything below must be done in this project.”

### Screen: Step 2 — Enable the Gmail API

**Purpose**
Turn on the Gmail API in the project from Step 1, and set the expectation that Google can take a few minutes to admit it.

**Layout Structure**
Shared chrome. Short ordered list, then a propagation note.

| Component | Type | State(s) | Behavior |

| Instructions | Ordered list | Default | Menu → APIs & Services → Library → Gmail API → Enable. Wait until Overview, Metrics, and Quotas are visible |

Open the library, confirm, mark done, go back.

**Interactions & Transitions**

**Data & Content**
Attestation only.

### Screen: Step 3 — Configure the consent screen

**Purpose**
Create the Google Auth platform consent screen and force an explicit choice between External (personal Gmail) and Internal (Workspace).

**Layout Structure**
Shared chrome. Two selectable cards for audience, then the field list for the wizard inside Google.

**UI Components**

| Component | Type | State(s) | Behavior |
|-----------|------|----------|----------|
| Open Google Auth platform | Secondary button | Default | New tab. Copy tells them to press Get Started if Google says it is not configured |
| Audience cards | Radio cards, two | Unselected, Selected, Focus | **External** — “Personal @gmail.com. Starts in Testing. Only people you list can connect.” **Internal** — “Workspace organization, and every user is inside it. No test users and no verification.” Selecting writes `account_type` |
| Field script | Description list | Default | App name `FinMail Agent`. User support email: their email. Contact email for notices. Finish: agree to the Google API Services User Data Policy, Continue, Create |
| Policy confirmation | Checkbox | Unchecked, Checked | “I finished Create on the consent screen.” Disabled until a card is selected |
| Mark done | Primary button | Disabled until checkbox | Records `steps.consent` and `account_type` |

**User Actions**

- Choose External or Internal. Changing the choice after Step 4 was skipped or completed reopens Step 4’s status: External sets it back to pending; Internal sets it to skipped.
- Mark done.

**Interactions & Transitions**
Selecting a card updates the rail label for Step 4 immediately: “Test user” or “Test user · not required.”

**Data & Content**
`account_type`: `external` or `internal` in `agent_state.json`.

**Empty State**
No card selected. The field script is visible either way, because both paths share app name and contact email. Step 4’s consequence is on the card, not hidden until later.

**Error State**
If they mark done with no card, the button stays disabled and the live region reads “Choose External or Internal first.”

**Accessibility Notes**
Radios share one `fieldset` and `legend`: “Who will use this app?” Cards are 72px tall minimum, full label is the accessible name.

**UX Rationale**
This is the fork that makes the rest of the guide wrong for one of the two personas. Putting it in a radio, with the consequence on the card, prevents Internal users from adding test users they do not have and prevents External users from thinking they can skip Step 4.

### Screen: Step 4 — Add yourself as a test user

**Purpose**
Put the exact mailbox address on the testing allow-list. This is the step the guide calls the most commonly missed, and the one that produces `access_denied`.

**Layout Structure**
Shared chrome. If Internal, the main column is a single skipped state. If External, it is a short task plus an address match.

**UI Components**

| Component | Type | State(s) | Behavior |
|-----------|------|----------|----------|
| Skipped panel | Status panel | Shown only when `account_type = internal` | “Internal apps do not use test users.” Primary button: Continue to read-only scope. Records `steps.test_user = skipped` |
| Open Audience | Secondary button | External only | Google Auth platform → Audience |
| Status cues | Checklist, not interactive | Default | Publishing status is Testing. User type is External. Then Test users → Add users |
| Address echo | Read-only field | Filled from Prerequisites | Shows `mailbox_address`. A text button “This is wrong” routes to Prerequisites without clearing later steps |
| Added confirmation | Checkbox | Unchecked, Checked | “I added this exact address and pressed Save.” |
| Mark done | Primary button | Disabled until checked | Records `steps.test_user = done` |

3. Only read-only is on until send is deliberately enabled. This row can show a computed hint “Send scope not in the current token” or “Send scope is present,” and the checkbox remains the owner’s.
4. Send is called from one function, reachable only from the owner’s send command. Hint text points at the agent, not something this screen can prove.
5. `SEND_ENABLED` kill switch and dry-run exist. Deep link to Settings.
6. Owner knows the revoke URL.
7. Email bodies are not written to logs. This row is an attestation aimed at the operator; the UI itself must not log bodies (Handoff).

**User Actions**
Check or uncheck rows, expand Why, open revoke, jump to Settings, reset.

**Interactions & Transitions**
Checking a row updates “N of 7 reviewed” in a polite live region.

**Data & Content**
Hints for rows 3 and 5 come from the token scopes and the process environment. All other rows are owner attestations. The screen says that at the top: “Checked items are your confirmation. FinMail verifies only the scope list and the kill-switch values.”

**Empty State**
Zero reviewed is the first-run state of this screen and is not dressed up as a failure.

**Error State**
If scope introspection fails, rows 3 and 5 drop the hint and stay usable. A one-line note: “Could not read the token to add a hint.”

**Accessibility Notes**
Each checkbox’s accessible name is the full requirement sentence. The progress text is not only a graphic.

**UX Rationale**
A security checklist that auto-checks itself would teach the owner to trust a green list. Separating the two machine-readable hints from the five human promises keeps the screen honest and still gives Ruth a list she can run before she copies files.

### Screen: Settings

**Purpose**
One place for the three ongoing controls: filesystem paths, dry run and the kill switch, and revoke-and-rebuild.

**Layout Structure**

- Header “Settings.”
- Three stacked sections, each with an `h2`, separated by 32px. No tabs: all three are short, and splitting them hides the kill switch.

**UI Components**

| Component | Type | State(s) | Behavior |
|-----------|------|----------|----------|
| Credentials path | Text input | Empty, Filled, Error | Binds to `GOOGLE_CREDENTIALS_PATH`. Blur validates that the path is absolute. Does not display file contents |
| Token path | Text input | Empty, Filled, Error | Binds to `GOOGLE_TOKEN_PATH`. Helper: “The app writes refreshed tokens here.” |
| Save paths | Primary button, section level | Default, Disabled, Saved | Disabled when either path is relative or empty. Saved state lasts 2 seconds |
| Dry run | Switch | On, Off | On by default. Helper: “On: FinMail drafts but does not send, except the send-to-self test.” |
| Allow approved sends | Switch | On, Off, Disabled | This is `SEND_ENABLED`. Disabled until Enable sending Stage C has succeeded. Helper while disabled: “Send a test to yourself first.” |
| Save switches | They save immediately | Saving, Saved, Error | A failed write reverts the switch and shows the error under it. Immediate save is appropriate because a stale kill switch is worse than an extra click |
| Revoke instructions | Static | Default | Link to `https://myaccount.google.com/permissions`. Text: remove FinMail Agent, then delete the local token |
| Delete local token | Destructive button | Default, Confirming | Confirm dialog names the file path. Deletes `token.json` only. Does not delete `credentials.json`. Sends the owner to Step 7 |

**User Actions**

- Edit paths and save.
- Toggle dry run.
- Arm or disarm send, when allowed.
- Open Google permissions.
- Delete the local token.

**Interactions & Transitions**
Switch moves 150ms. Destructive confirm is a dialog, same focus rules as Enable sending.

**Data & Content**
Paths and flags from the process environment and `agent_state.json`. If the UI and the environment diverge, show the environment value and the note “Started with SEND_ENABLED={value}. Restart the process after a change if the agent reads this only at startup.” That restart rule is an open engineering question; the copy must match actual process behavior before build (see Open Questions).

**Empty State**
Paths empty on a fresh machine: inputs show the placeholder `./credentials.json` is not accepted. Placeholder text: “Absolute path.”

**Error State**

- Relative path: “Use an absolute path. A relative path breaks when the agent starts from another directory.”
- Path points at a directory: “That is a folder, not a file.”
- Save failed: “Could not write agent state.” Retry.

**Accessibility Notes**
Switches are `role="switch"` with `aria-checked`, and the visible On/Off text is adjacent. Delete local token is a button, not a link, and is not the last unlabeled icon in the page.

**UX Rationale**
Paths, the kill switch, and revoke are the three settings that survive after the wizard is finished. One page keeps the dangerous switch in view beside the recovery action. Immediate save on the switch avoids a world where the owner thinks send is off and the process still has the old value because they did not press Save.

### Screen: WhatsApp — connection and token alerts

**Purpose**
Tell the owner, in the thread they already watch, that the agent has stopped reading or sending. The console is where they fix it. WhatsApp is where they learn they should.

**Layout Structure**
One short message. No card chrome we control beyond line breaks. First line is the condition. Second line is the single action. Third line, only when useful, is the mailbox address.

**UI Components**

| Component | Type | State(s) | Behavior |
|-----------|------|----------|----------|
| Alert message | Outbound WhatsApp text | Token invalid, API disabled, Rate limited, Send refused | Sent at most once per condition per 6 hours, so a polling loop cannot flood the owner |
| Address line | Text | Included when known | “Mailbox: ada@gmail.com” |

Copy:

- Token invalid: “FinMail cannot read Gmail. The token was refused. Open the setup console on your computer and re-authorize. Do not create a new Google Cloud project.”
- API disabled: “Gmail returned ‘API not enabled’ for this project. In the console, open Step 2 and confirm the top bar still says FinMail Agent. If you just enabled it, wait a few minutes.”
- Rate limited: “Gmail asked FinMail to slow down. It will retry later. No action unless this repeats through the day.”
- Send refused: “I kept that draft. Sending is off (`SEND_ENABLED`). Arm it in the console only after a send-to-self test.”

**User Actions**
Read. Open the computer. Reply is not required and is not parsed as a repair command.

**Interactions & Transitions**
No animation. Delivery is WhatsApp’s.

**Data & Content**
The alert may include the Google error code. It must not include message bodies, subjects, or tokens.

**Empty State**
No alert when the last poll succeeded. Silence is the healthy state. Do not send a daily “still connected” message in v1.

**Error State**
If WhatsApp itself rejects the alert, the console Home banner is the fallback the next time the owner opens it. The agent logs the delivery failure without the alert body if that body ever contains mail content. These alerts do not contain mail content.

**Accessibility Notes**
Plain text, full sentences, no color-only status, no emoji as the only signal. A single status emoji is allowed as a prefix if the sentence still stands without it. Default is no emoji, because these are failure messages and the guide’s owner is in a repair mindset.

**UX Rationale**
The returning persona hears about failure on WhatsApp and repairs it at a desk. The message’s job is to stop the most damaging wrong repair (“create another project”) in the same bubble as the symptom.

### Screen: WhatsApp — financial mail digest

**Purpose**
Deliver the result of `fetch_emails` for the configured query (the guide’s example is `newer_than:2d (invoice OR receipt OR statement)`) as a short list the owner can act on.

**Layout Structure**
One message per poll that found new ids, not one message per email. A header line, then up to five items. If more than five are new, the rest are counted.

**UI Components**

| Component | Type | State(s) | Behavior |
|-----------|------|----------|----------|
| Header | Text | Default | “3 new financial emails · ada@gmail.com” |
| Item | Text block | Default | `{n}. {From display name} — {subject}` and a second line `{one-line reason or category if the classifier produced one}`. `n` is the draft index used by `send N` |
| Overflow | Text | Shown when more than 5 | “+4 more. Ask ‘show more’ to see the next 5.” |
| Empty poll | No message | Default | A poll with zero new ids sends nothing |

**User Actions**

- Read.
- Reply `show more`.
- Reply `open N` to receive the draft review for that index.
- Reply `help` to receive the three commands `show more`, `open N`, `send N`.

**Interactions & Transitions**
Items keep their index until the owner sends, skips, or a new poll rebuilds the list. A rebuild message says “Indexes refreshed” before the new list, so `send 2` cannot hit a different draft than the one they just read.

**Data & Content**

- From, subject, and a single-line classifier label. The body is not in the digest.
- Ids are stable agent draft ids, not raw Gmail ids, in the owner-facing text.

**Empty State**
No WhatsApp message. The console does not show this list either in v1.

**Error State**
If classification fails and mail metadata succeeded, send the digest without the category line and add “Classification is unavailable; subjects only.” If fetch fails, send the token/API alert instead of an empty digest. Never send “0 emails” as a message.

**Accessibility Notes**
Numbered lines in reading order. No ASCII tables. Subjects that are long are truncated at 80 characters with an ellipsis; `open N` has the full subject.

**UX Rationale**
Batching respects attention and WhatsApp’s pace. Stable indexes are the safety property behind `send N`: the command must resolve to the draft the owner looked at.

### Screen: WhatsApp — draft review

**Purpose**
Show one draft clearly enough to approve, and make the send command unambiguous.

**Layout Structure**
A single message:

1. “Draft 2 of 5”
2. To, Subject
3. The draft body, truncated at 700 characters if needed, with “Reply `full 2` for the rest.”
4. The only send instruction: “Reply `send 2` to send this draft. Reply `skip 2` to drop it.”

**UI Components**

| Component | Type | State(s) | Behavior |
|-----------|------|----------|----------|
| Header | Text | Default | Index and total in the current list |
| To / Subject | Text | Default | `To:` is the reply-to address the agent will actually use |
| Body | Text | Short, Full | Short by default |
| Command line | Text | Default | Names `send N` and `skip N` for this N only |

**User Actions**

- `send N` — handled by the send confirmation pattern.
- `skip N` — drops the draft, confirms “Skipped 2. Nothing was sent.”
- `full N` — sends the remainder of the body in a follow-up message.
- Any other reply is treated as conversation, not as approval. The agent must not interpret “yes” or “ok” as send.

**Interactions & Transitions**
None visual. The next message is either confirmation, a refusal, or the rest of the body.

**Data & Content**
Draft fields the guide’s `send_reply` expects: `to`, `subject`, `body`, `in_reply_to`, `thread_id`. The owner sees to, subject, and body. Thread headers stay internal.

**Empty State**
If `open N` does not match a current index: “There is no draft 2. Reply `show` for the current list.”

**Error State**
If the Gmail id 404s because the mail was deleted: “That message is gone from Gmail. I dropped draft 2.” It is removed from the index.

**Accessibility Notes**
Labels “To” and “Subject” are words. The send command is a separate final line so screen-reader users on WhatsApp do not hear it buried in the body.

**UX Rationale**
Approval is a command with an index, not a natural-language yes, because the cost of a wrong send is an email from the owner’s real address. Forcing `send N` is a speed bump the guide already assumes (“only from the owner’s send command”).

### Screen: WhatsApp — send confirmation

**Purpose**
Close the loop on `send N` with one of four outcomes: sent, dry-run, refused by the kill switch, or failed.

**Layout Structure**
One short message. Outcome first, then the recipient, then any identifier.

**UI Components**

| Component | Type | State(s) | Behavior |
|-----------|------|----------|----------|
| Sent | Text | Success | “Sent draft 2 to vendor@example.com. Gmail id {id}.” |
| Dry run | Text | Suppressed | “Dry run is on. Draft 2 was not sent to vendor@example.com.” |
| Kill switch | Text | Refused | “Sending is off. Draft 2 was not sent. Arm `SEND_ENABLED` in the setup console if you mean to.” |
| Failed | Text | Error | “Gmail did not send draft 2. {mapped reason}. The draft is still here.” |

**User Actions**
Read. Retry by sending `send N` again after a failure. A second `send N` after success replies: “Draft 2 was already sent. I will not send it again.”

**Interactions & Transitions**
The draft is marked sent in `agent_state.json` before the success message is attempted. If WhatsApp delivery of the confirmation fails, a retry of the confirmation must not send the email again.

**Data & Content**
Recipient and Gmail message id. No token, no raw MIME.

**Empty State**
Not used. A `send` command with a missing index uses the draft review empty copy.

**Error State**
Mapped with the same phrases as Step 8 where they overlap (invalid token, insufficient scope, rate limit). Insufficient scope adds: “The token does not include send. Finish Enable sending.”

**Accessibility Notes**
Outcome is the first words: “Sent”, “Not sent”, or “Failed”.

**UX Rationale**
The owner must be able to tell a dry run from a real send in the first line, including when they are glancing at a lock screen. Identical layouts with a different verb at the start support that glance without training.

## 7. Design System

The console looks like a calm operations tool: warm paper background, ink text, one deep teal for actions. Gold is a hairline accent for the wordmark and focus decorations. It is not used for text, because `#C4A35A` on paper is about 2.2:1. WhatsApp messages use WhatsApp’s chrome; we specify copy, not a second visual system inside the thread.

### 7f. Core component specs

#### Button

Variants: Primary (fill `color-primary`, label white), Secondary (white fill, 1px `color-primary` border, label `color-primary`), Ghost (transparent, label `color-primary`), Destructive (fill `color-error`, label white).

Sizes: SM 32px height, 12px horizontal padding, 14px label, used only in card headers. MD 40px, 16px padding, default. LG 48px, 20px padding, used for Welcome’s start and the wizard’s primary footer action.

States: Default, Hover (primary moves to `color-primary-hover`), Active (same fill as hover, translate 1px down), Focused (2px `color-focus` ring, 2px offset), Disabled (60% opacity, no hover, `aria-disabled` plus a reason when the reason exists), Loading (label replaced by “Working…” plus a spinner, width locked so the footer does not jump).

- Do: one Primary per screen region.
- Do: put the reason for Disabled in helper text.
- Don’t: use Destructive for “delete token” without the confirm dialog.
- Don’t: use Primary for “Open Google Cloud.” Leaving the app is Secondary.

#### Text input

MD height 44px, padding 12px, radius `radius-sm`, border `color-border`. Focus: border becomes `color-primary` and the focus ring appears. Error: border `color-error`, helper text in `#7A1F1F` on the surface, plus an error icon. Disabled: background `#F6F4EF`.

- Do: visible label above the field, never placeholder-as-label.
- Don’t: put a scope URL or a filesystem path in a proportional input without offering Copy and a mono font.

#### Card

White surface, `shadow-sm`, `radius-md`, padding 24px desktop / 16px narrow. Status cards include a text status in Label style at the top.

- Do: one idea per card on Home (Read, Send, Token).
- Don’t: make the whole card a single click target when it contains two actions.

#### Dialog

Surface white, `shadow-md`, `radius-lg`, max width 440px, padding 24px. Title is H3. Primary and Cancel aligned to the end of the footer. Cancel is Ghost and is the safe choice; for destructive confirms, Cancel has initial focus.

- Do: trap focus, close on Esc, restore focus.
- Don’t: open a dialog for a successful test. Success is inline.

#### Toast

Not used in v1. Success and failure stay next to the control that caused them, because the owner may be looking at a Google window and a toast disappears. The one exception is Copy confirmation, which is inline on the button (“Copied”).

#### Navigation rail

Width 240px, background `#E7EEF2`, item height 40px, padding-left 16px. Current item: white pill, text `color-primary`, `aria-current`. Done items: text primary plus the word “Done” in caption style, not a checkmark alone. Disabled items: `color-text-secondary` and the reason in the item’s description.

- Do: keep Enable sending visible while disabled.
- Don’t: badge the rail with counts of emails. That pulls mail content into setup.

#### Status chip

Label font, padding 4px 8px, `radius-full` only if height stays at least 24px. Text is “Pass”, “Fail”, “Checking”, “Skipped”, “Off”, “Armed”. Background is the matching surface token; text is the darker ink.

- Do: include the word.
- Don’t: rely on a colored dot.

## 8. Interaction and Animation Guidelines

- Duration: 150ms for color, opacity, and checkbox; 200–240ms for step changes and the rail appearing; dialogs 200ms. Nothing at 400ms or above in v1. There is no page transition that deserves it.
- Easing: `ease-out` for the rail and for panels entering; `ease-in` for dialogs leaving; `ease-in-out` for the switch thumb.
- Motion is confirmatory. A checkmark does not bounce. A skeleton is the loading pattern for the connection test and the prerequisite rows.
- `prefers-reduced-motion: reduce` removes the rail slide, the step fade, and the switch travel. State changes are instant. Skeletons become static gray bars.
- Buttons: hover and focus only. No ripple.
- Switches: thumb travels the track. The On/Off word updates at the start of the travel, not at the end, so a reduced-motion user and a sighted user read the same state immediately.
- There is no pull-to-refresh. Retest is a button, because an accidental gesture that hits Gmail is a rate-limit risk.
- The credentials watcher on Step 6 is the only poll. It runs every 2 seconds and only while that step is visible.
- WhatsApp has no motion spec beyond what WhatsApp does.

## 9. Accessibility (WCAG 2.1 AA)

| Requirement | Standard | Implementation note |
|-------------|----------|---------------------|

## 11. Edge Cases and Error Handling

| Scenario | Behavior | Recovery |
|----------|----------|----------|
| No internet while a local page is open | Pages already loaded stay usable. A test or OAuth start fails with “FinMail could not reach Google.” | Retry on the same step. Do not clear completed steps |
| No internet on first paint | The app is local, so the HTML still loads. Google buttons remain, and fail only when followed | The owner can read ahead |
| Token file deleted outside the app | Next launch opens Step 7 with Token status Absent. Steps 1–6 stay done | Authorize again |
| `credentials.json` replaced with a Web client | Step 6 returns to Invalid and Step 7’s Authorize disables | Replace the client |
| External testing token older than 7 days | Home Token card shows the caution as soon as a read fails with `invalid_grant`, even if the 6-day warning was missed | Re-authorize. Link the publish explanation |
| Owner publishes the Google app | A Setting note “I published the app” clears the 7-day warning. The console cannot read Publishing status from Google in v1 | Attestation, labeled as such |
| Session / local server restarted | `agent_state.json` restores step status. OAuth waits do not survive a restart | Step 7 returns to Default and offers “Check for token.json” |
| Gmail 5xx | “Gmail had an error. Nothing here was changed.” | Retry. After two failures, point at Troubleshooting |
| Clock skew causing `invalid_grant` | Mapped as invalid token, with an added sentence: “If this repeats immediately, check that the computer’s clock is correct.” | Re-authorize after the clock is fixed |
| Owner on the no-browser path | Step 7 does not auto-open a browser. Move to server becomes available only after a token exists | Authorize on a laptop and copy the files |
| `SEND_ENABLED` on, Dry run on | Send card reads “Dry run.” WhatsApp `send N` gets the dry-run confirmation. Send-to-self is the documented exception | Leave dry run on until they trust drafts |
| First run, no files | Welcome, not an empty dashboard | Start setup |

## 14. Handoff Notes

- **Design tool:** Figma, one file, one page per screen in Section 6, components from Section 7f with variants for every state in the tables.
- **Tokens:** CSS custom properties on `:root`, names exactly as in Section 7. Export the same names to Figma variables.
- **Prototype fidelity:** High fidelity for Steps 6, 7, and 8 and for Enable sending, because those are the error-prone screens. Mid fidelity is enough for Security and Move to server.
- **Assets:** No illustrations in v1. Status icons as 16px SVG (pass, fail, warning, lock) with the meaning duplicated in text. IBM Plex Sans and IBM Plex Mono as local files.
- **Engineering notes:**
  - Bind the server to loopback only. Refuse to start if the bind address is not `127.0.0.1`.
  - Never render or log `credentials.json`, token material, or email bodies. The draft body is allowed in the WhatsApp payload the owner requested and nowhere else.
  - Step 6’s client-type check is “JSON has `installed` and not `web`.” Mask any client id in the UI.
  - Write `token.json` and `credentials.json` mode `600` when the platform supports it.
  - Scope strings in the UI must be the same constants the OAuth flow requests. One module owns the list.
  - `send_reply` in the guide sets `In-Reply-To`. The send-to-self test is not a reply and must omit those headers rather than sending empty ones.
  - Cap Gmail list calls at 25, matching the guide’s rate-limit note.
  - Idempotency: record a draft as sent before announcing success on WhatsApp.
  - Do not introduce a second send path from the console. The console’s only send is the send-to-self test.
- **Copy source:** When Google renames a menu, update the instruction strings in one content file that Troubleshooting and the wizard share, so a label fix does not drift between them.
- **Out of scope for design:** Python virtualenv creation, `gmail_service.py`, OpenAI prompts, and systemd unit files. The env template names them and stops there.
